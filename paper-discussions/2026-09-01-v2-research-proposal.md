## 1. 研究背景与意义

设备驱动是操作系统内核中数量最大、出错最多的组成部分，在 Linux 内核代码中占比超过一半。随着嵌入式与异构平台的多样化——Zephyr/FreeRTOS 等 RTOS、裸机固件、Rust 新内核、用户态测试环境——把为 Linux 编写的驱动**翻译**到其他运行环境成为反复出现的系统工程问题。

驱动翻译的根本困难在于：**驱动源码不是同质程序**。它交织着两类关注点：

- **操作系统集成逻辑**：资源获取（`devm_*`）、子系统注册、回调表、锁与对象生命周期——这些在 Linux 之外往往不存在；
- **设备核心逻辑**：寄存器读写、总线事务、路径条件、软件缓冲区与设备寄存器间的数据搬运——这些才是跨平台必须保真的硬件行为。

对本项目 19 个驱动语料的测量显示：非空源行中仅 **9.5%** 属于设备核心，**90.5%** 是框架粘合（框架入口 32.6% + 胶水/辅助 25.7% + 文件级样板 32.2%）。任何"逐语法单元翻译"的方法都注定把 90% 的 Linux 特有结构带进目标程序。

大语言模型（LLM）的出现改变了翻译方法的格局，但也引入了新的风险。直接让 LLM 翻译完整驱动时，模型面对的是动辄数千乃至数万行、由大量函数与代码块交织而成的源文件（本语料中 dwc2 单驱动即 21,668 行、445 个函数），而真正需要保真的设备核心行为仅占约 9.5%——关键的一次寄存器写、一个中断应答、一次缓冲区游标推进，散落在长上下文的各个角落，被海量框架样板所流没。代码量过大、代码块过多导致模型注意力波稀释：它难以在逐块处理中持续锚定这些零散的协议细节，只能退回记忆中的（往往过时的）API 惯用法去"补全"协议行为——于是产生幻觉的寄存器操作、过时的内核 API、遗漏的中断应答或被重排的缓冲区更新，而这些错误恰恰是编译无法发现的。本项目开发期的真实事故（明确禁止 DMA 配置的 QEMU edu prompt 仍产出 DMA 候选，引发中断风暴挂死 guest）证明了这一风险的现实性。这也正是本研究把翻译面收缩到结构化证据契约的动机之一：DW 案例中 1,844 行源码对应的证据包仅数十 KB，模型注意力被集中在"表达已确立的操作"而非"在万行代码中重新发现语义"。

本研究的核心主张：**驱动翻译的关键问题不是"用规则还是用 LLM"，而是"允许非确定性出现在哪里"**。我们把 LLM 夹在两个确定性阶段之间，用证据契约约束其行为，用确定性验证门验收其产物，构成一个可信的混合翻译框架。

## 2. 研究问题与目标

**核心研究问题**：如何构建一个翻译框架，使得从完整 Linux C 驱动源码出发，能够为多个异构后端（用户态 harness、裸机 C、Linux 内核模块、Rust `no_std`）生成**设备核心行为可验证保真**的驱动代码，同时让 LLM 的非确定性被限制在可验收的边界内？

分解为五个子问题：

- **RQ-A（表示）**：什么样的中间表示能同时捕获寄存器身份/宽度/顺序、路径谓词、类型化总线事务、以及软件缓冲区与寄存器之间的数据流，且与后端无关？
- **RQ-B（提取）**：如何从交织着框架代码的完整驱动源码中确定性提取该表示，包括宏偏移、头文件内联访问器、包装函数、分支守卫与读-改-写模式？
- **RQ-C（翻译）**：如何设计 LLM 的输入边界与后端插件协议，使模型只做"重新表达"而非"重新解释"，且新增后端无需修改提取与验证？
- **RQ-D（验证）**：什么样的验证门能在多大范围内机械地验收候选代码，其声明范围（与不声明范围）如何显式化？
- **RQ-E（评估）**：如何在真实驱动语料上量化提取保真度、翻译就绪度与端到端正确性，并诚实区分编译/就绪/等价三个层次？

**研究目标**：建成上述框架的原型系统并完成系统性评估；产出可复现的版本化实验产物。

## 3. 国内外研究现状与不足

| 研究路线 | 代表工作 | 对驱动翻译的不足 |
|---|---|---|
| 确定性源码翻译 | C2Rust、Corrode、LLVM 基础设施 | 保留源程序分解结构，产物仍绑定 Linux API 与生命周期；设备协议仍隐式；换后端需人工重新恢复 |
| 直接 LLM 翻译 | CodeT5 及现代代码 LLM | 语义发现与代码发射一肩挑；幻觉寄存器行为/过时 API；编译无法检测类型正确但语义错误的输出 |
| 混合翻译 + 反馈 | TransCoder、CoTran | 有验证反馈但不定义模型可重新解释的范围；候选空间仍包含任意遗漏与发明 |
| 驱动分析与合成 | SDV/SLAM、Devil+、Dingo/Termite、KLEE、S2E | 针对框架协议、需手写设备/OS 模型、或依赖可执行环境；无法从既有 Linux 驱动自动提取紧凑硬件契约作为翻译输入 |
| 翻译验证 | Barthe 等、CreLLVM、Alive2 | 提供有界验证思想，但面向编译器优化而非生成式翻译 |

**定位**：本研究把确定性语义边界移到**生成之前**——这是与上述各路线的本质区别。

## 4. 已有工作基础（前期成果）

本项目已完成框架原型与第一轮评估（即 v2 论文所报内容），具备扎实起点：

1. **混合提取管线**：libclang AST 分析（预处理记录宏解析、抽象存储 Σ: Var→𝒱、六类抽象值、谓词栈、RMW 折叠含 Ite 分支变换、深度受限包装内联与摘要）+ LLVM IR 证据恢复（`-O1` 内联后从 `asm sideeffect` 模式与 GEP 回溯恢复头文件内联 MMIO），按 `(function, offset)` 保守合并。
2. **RIS 证据语言（三层操作模型）**：寄存器操作（R/W/RMW，宽度 B1–B8）/ 类型化事务（regmap、I2C/SMBus、MFD）/ 功能状态操作（`VALUE`/`STATE`/`OUT`，捕获缓冲区↔寄存器数据流）；地址三分类（Symbolic/Fixed/Computed，绝不伪造符号名）。
3. **语义推断与后端绑定**：FunctionSpec/DeviceSpec（Hoare 风格前后置条件、回调表证据优先的角色推断）、BindSpec 与六节证据 JSON（LLM 唯一输入，不含源码）。
4. **四个后端插件与验证门**：harness C、裸机 C、Linux 内核模块、Rust `no_std`（tock-registers）；编译 → lowering 回执对账（存在性/恰好一次/种类匹配/摘要一致性）→ trace oracle（子序列 + 分支敏感变体）→ 有界修复（≤3 轮）。
5. **评估结果**：19 驱动 485 操作（77.7% 符号地址、73 RMW、123 条件、157 寄存器）；编译 19/19/18 与严格就绪 4/4/2 的**刻意分离**；3 个多源 USB 模块（19 TU、27,447 行、跨 TU 边 223/223、dwc2 4,250 操作）；QEMU 双切片（edu 值级 6/6、ftgpio010 逐回调 13/13）；DesignWare APB SSI 四后端端到端（1,844 行 → 828/581/276 行，18 项机器可检清单）；zero-shot 留出集 12 驱动（12/12 编译、7/12 与 5/12 严格就绪）；LLM 闭环 6/7（86%）。
6. **可复现基建**：版本化 `./run.sh` 管线、`generated_results.tex` 宏生成、树内反特化 guard 强制的冻结留出集。

## 5. 研究内容与技术方案

### 5.1 总体架构

```
完整 Linux 驱动源码
   │
   ├─ AST 路径（libclang：宏、数据流、谓词栈、内联/摘要）
   ├─ IR 路径（clang -O1：内联 asm sideeffect 模式、GEP 偏移）──┐
   │                                                            ↓ 保守合并
   └──────────────────► RIS 证据契约（三层操作 + 地址三分类）+ Function/DeviceSpec
                                   │
                        证据 JSON（六节，无源码）
                                   ↓
                     LLM 桥 × 后端插件（prompt.md + BindSpec）
                                   ↓
                          不可信候选代码（四后端）
                                   ↓
              验证门：编译 → 回执对账 → 原语形状 → trace oracle
                                   │ 失败（结构化反馈，≤3 轮）
                                   └────────► 有界修复 ↺
```

### 5.2 五项研究内容

- **W1 证据契约语言（RIS）的完善**：在三层操作模型上补齐 DMA 描述符与异步 I/O 的建模（当前明确不支持）；扩展跨中断状态机的状态可见性分析；研究 RIS 的指称语义与有界精化声明（当前只有语法与操作性语义）。
- **W2 提取保真度的系统测量**：当前 485 操作等数字是"内部特征化指标"，非相对真值的精确率/召回率。建立分层人工标注真值（操作种类/地址/宽度/值/顺序/守卫/回调/状态流八维）或源-目标差分 trace，量化提取漏报；测量深度 3 内联截断的覆盖代价并验证每个截断路径都转为就绪阻塞项。
- **W3 验证门的攻击性评估（mutation testing）**：系统构造变异体（新增 DMA/IRQ/MMIO 操作、重复访问、错误基址、错误写值、守卫篡改），检验静态门与 QEMU 门能否拒绝——把"验证门确立了什么"从声明变成测量。
- **W4 LLM 翻译的受控评估与消融**：固定模型/版本/prompt/温度/种子，在留出 eligible 驱动上重复试验，报告首过率、修复通过率、成本与延迟；与基线对比——直接源码 LLM、C2Rust、确定性发射器；消融 IR 证据、功能状态层、回执机制、修复循环各自的贡献。
- **W5 后端等价性与扩展**：Rust 后端的固定工具链 AST/HIR 回执检查与模拟器/硬件执行；类型化事务在真实 regmap/I2C/MFD 驱动上的选择子/宽度/缓存/顺序检查；网络驱动、DMA engine、regulator 子系统建模；物理硬件（SPI 控制器）上的验证。

### 5.3 关键技术问题与对策

| 技术风险点 | 对策 |
|---|---|
| 提取漏报不可见（accounting 只计已发射操作） | W2 分层标注/差分 trace；把 provenance 计数与真值召回率分开报告 |
| `(function, offset)` 合并键碰撞 | 引入调用点实例与访问重数进合并键；碰撞率测量 |
| 验证门子序列匹配放过额外访问 | W3 变异测试显式测量放过率；结果如实报告为门的声明边界 |
| LLM 输出随模型漂移 | 桥接口与端点解耦；验收标准与模型无关；固定版本重复试验 |
| 严格就绪比例低（2–4/19） | 不是缺陷而是保守性设计；通过 W1/W2 扩大可建模面，逐类消除阻塞项（未知变换、不安全动态地址、未绑定子系统状态） |

## 6. 创新点

1. **证据契约驱动的混合翻译架构**：首次把"确定性边界"置于生成之前，LLM 只翻译结构化证据（RIS + 绑定 + 事实）而非源码，回答了"非确定性允许出现在哪里"。
2. **三层 RIS 证据语言**：寄存器/类型化事务/功能状态的操作分层，特别以 `VALUE/STATE/OUT` 捕获缓冲区-寄存器数据流——解决"寄存器顺序全对却传不出一个字节"的功能等价缺口。
3. **AST + LLVM IR 双路提取与保守合并**：宏名、谓词、回调绑定来自 AST；头文件内联 MMIO 来自 IR；互补而非替代。
4. **lowering 回执机制**：每个操作携带 `op_id` 与规范化契约摘要，生成侧强制"恰好一次"回执，把 LLM 的结构性义务变成机械可查。
5. **编译 / 严格就绪 / 等价三级诚实评估**：拒绝把编译当语义正确，未关闭项（如 DW 清单中 Linux Kbuild 与 Rust 数据流失败）逐项如实报告。

## 7. 研究计划与时间安排（2026-09 起，12 个月）

**阶段一（M1–M3）：证据链修复与复现加固**
- 修复 QEMU 实验可复现性（qemu.json schema 漂移、宏生成器崩溃——见 quantification-review P0-1）；
- 把 18 项 DW 清单落为版本化脚本与逐项结果产物（P0-2）；
- 补齐分母与名单：68 个未解析调用给数、表 1/2 子集选择标准、严格就绪点名、synthesis-eligible 指标给下游消费者或删除；zero-shot 12 例并入主评估。

**阶段二（M3–M6）：提取保真度测量（W2）**
- 八维分层标注真值（至少 10 个驱动）或源-目标差分 trace 基础设施；
- 精确率/召回率首次测量；深度 3 截断覆盖分析；
- 产出：提取质量报告，替换"内部特征化指标"表述。

**阶段三（M5–M8）：验证门攻击性评估（W3）与 LLM 受控试验（W4）**
- 变异体语料与门的拒绝率测量；
- 固定模型重复试验（≥5 eligible 驱动 × N 次采样）：首过率/修复率/成本/延迟；
- 基线对比（直接 LLM、C2Rust、确定性发射器）与四项消融。

**阶段四（M7–M11）：表示与后端扩展（W1/W5）**
- DMA 描述符与异步 I/O 建模设计；
- Rust 后端等价性检查链（固定工具链 + HIR 回执 + 模拟器执行）；
- 类型化事务在真实 regmap/I2C/MFD 驱动上的验证；
- 至少一个网络驱动与一个物理 SPI 硬件验证点。

**阶段五（M11–M12）：整合与论文定稿**
- 全部结果经 `./run.sh` 再生；EXPERIMENT_DEBT 清单逐项关闭或降级为声明边界；
- 论文修订投稿；开源 artifact（ASAP/ARTIFACT 评估目标）。

## 9. 风险分析与应对

| 风险 | 概率 | 应对 |
|---|---|---|
| 人工标注真值成本过高 | 中 | 优先差分 trace 自动化；标注限定分层抽样子集 |
| 变异测试显示门放过率过高 | 中 | 结果本身是贡献（量化声明边界）；据此收窄门或增加 oracle 层级 |
| LLM 端点/版本不可控 | 高 | 已有端点解耦设计；报告固定版本结果并声明适用范围 |
| DMA/并发建模规模超预期 | 高 | 降级为"就绪阻塞项"路线：建模不了的不静默近似，保持诚实评估 |
| 物理硬件验证环境受限 | 中 | 以 QEMU 机器模型 + FPGA/开发板双轨备选 |
