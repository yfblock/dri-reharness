## 一、核心论证主线

**一句话**：论文把"驱动翻译"重构为一个**证据流问题**——确定性分析从完整 Linux 驱动中提取设备核心的**证据契约**，LLM 只负责在契约内做目标语言**表达**（从不接触源码），确定性验证门做**有界验收**，失败反馈驱动**有界修复**。

全文的题眼在引言中一句点破：

> 核心问题不在于翻译应该用规则还是 LLM，而在于 **"允许非确定性出现在哪里"**。

三个确定性锚点夹住唯一的概率性环节（LLM 发射）：

```
确定性提取（AST + LLVM IR → RIS 证据契约）
        ↓  证据 JSON（唯一输入，不含源码）
非确定性发射（LLM + 后端 prompt → 候选代码）
        ↓
确定性验证门（编译 → 回执对账 → trace oracle）⇄ 有界修复（≤3 轮）
```

支撑这条主线的前提判断（引言 + §2）：

1. **驱动不是同质程序**：OS 集成逻辑（资源获取、子系统注册、回调、生命周期）与设备核心逻辑（寄存器交互、总线事务、路径条件、缓冲区数据搬运）交织在一起；
2. **两个极端都失败**：规则翻译（C2Rust）完整保留源结构 → 产物仍绑定 Linux、协议仍隐式；直接 LLM 翻译让模型同时负责语义发现与代码发射 → 幻觉寄存器行为/过时 API（有 QEMU edu DMA 中断风暴的 war story 为证）；
3. **可量化**：语料中仅 **9.5%** 的非空源行属于设备核心，**90.5%** 是框架粘合——这正是语义边界设计所针对的构成（图 3）；
4. **由此得出的方法**："**分析完整源码、翻译更小的语义契约**"——不删除粘合代码、不假装框架无效果（回调绑定决定角色、资源获取确立 MMIO 基址、框架分支守卫寄存器写），只把设备核心效果收入跨后端契约。

## 二、各章节行文逻辑

### §1 引言 — 重新定义问题，而非介绍工具

- 从"驱动移植是反复出现的系统问题"出发，立即指出"源到源转换"这一常见描述的误导性：驱动是两类关注点的混合体。
- 用两个极端（确定性翻译 / 直接 LLM）的失败模式夹出中间立场，其中直接 LLM 的失败用开发期真实事故佐证（禁 DMA 的 edu prompt 仍产出 DMA 候选、中断风暴挂死 guest 摧毁反馈通道）。
- 关键一跃：把问题从"选哪种翻译器"重构为"非确定性放在哪里"，然后给出三段式答案（提取 → 发射 → 验证门）。
- 用 DesignWare 案例的行数缩减（1,844 行源码 → 828 Linux / 581 裸机 / 276 Rust）预演"翻译面缩减"论点，并立即自我限定：缩减不是正确性论证，只是缩小 LLM 的语义与文本搜索空间。
- 五项贡献按管线顺序排列：提取管线、RIS 证据语言、受约束混合翻译器（四后端共享一份证据契约）、验证门、可复现评估。

### §2 研究动机 — 交织结构 + 现有边界的失效

- **2.1** 用 probe / 中断回调 / 传输回调三个具体场景说明交织：寄存器访问藏在宏和 `static inline` 头函数里、经子系统 ops 表注册。随后立起方法论公理：跨后端表示必须分离两类关注点，**又不能假装框架代码没有效果**。
- **2.2** 按四条战线逐一批判，每条都落到"为什么不能定义翻译边界"：
  - **确定性源码翻译**（C2Rust/LLVM/CodeT5）：保留分解结构 → `devm_*`、回调表、锁、生命周期全部存活；引出 9.5% vs 90.5% 的量化；
  - **直接 LLM 翻译**：语义发现 + 发射一肩挑 → edu 事故、版本不兼容 API、编译无法检测的多余寄存器写；
  - **确定性语义边界**（TransCoder/CoTran）：仅有反馈不定义模型可重新解释的范围；
  - **早期驱动分析/合成系统**（SDV、Devil+、Dingo/Termite、KLEE/S2E）：或针对框架协议、或需手写规约、或依赖可执行环境，都不能从既有 Linux 驱动提取紧凑硬件契约。
- 收束句："reharness 把确定性边界移到了**生成之前**"——为 §3 铺路。

### §3 系统设计与证据契约 — 先定义"翻译什么"，再讲"怎么得到"

- 四阶段管线总览（图 1），核心设计原则一句话：**证据契约——下游阶段被指示"重新表达"而非"重新解释"**。
- **注意章节顺序的深意**：v2 先讲契约（§3 RIS 语言）再讲提取（§4 前端）——先立目标再讲手段，这是翻译框架叙事；旧稿是先提取后规约的提取器叙事。
- **3.2 RIS 三层操作模型**（论文最核心的技术资产）：
  - 第 1 层寄存器操作 `R/W/RMW`（宽度 B1–B8 贯穿到代码生成选原语）；
  - 第 2 层类型化事务 `TXREAD/TXWRITE/TXUPDATE`（regmap/I2C/MFD，句柄与选择器分离，不与内存地址混淆）；
  - 第 3 层功能状态 `VALUE/STATE/OUT`（缓冲区↔寄存器的数据流——没有它，生成的驱动"能按正确顺序摸对寄存器却传不了一个字节"）。
  - 配套：地址三分类（Symbolic/Fixed/Computed，**绝不伪造符号名**）、表达式代数（含 Ite）、谓词栈控制流、清单 1（DW SPI 发送循环 `VALUE → STATE → W → STATE`）作为三层交错的实证。
- **3.3/3.4** 语义推断（FunctionSpec/DeviceSpec，回调表证据优先于名字启发式）与 BindSpec + 证据 JSON（六个节；LLM 的唯一语义输入，**原始 C 源码任何情况下不序列化**）。

### §4 设备核心契约提取 — 翻译前端的三件武器

- **4.1 AST 路径**：宏表（预处理记录）、抽象存储 Σ: Var → 𝒱 与六类抽象值（BasePtr/Offset/ReadTaint/Const/SymExpr/Top）、地址解析的核心地位、谓词栈（then 压条件、else 压否定）、RMW 折叠（含分支相关变换的 Ite 重构）、深度受限的包装内联 + **包装摘要**（对 `dw_readl/dw_writel` 这类单行转发器推断紧凑映射）。
- **4.2 LLVM IR 证据恢复**：坦承 AST 路径的盲点（头文件 `static inline` 访问器），`clang -O1` 内联后从 `asm sideeffect` 模式恢复读/写、经 GEP 回溯偏移、经调试信息归属源函数；按 `(function, offset)` 保守合并——并诚实声明该键会碰撞，是明确限制。
- **4.3 功能状态与类型化事务**：ValueBind/StateWrite/OutputWrite 的识别规则（只保留被后续操作消费的绑定；局部临时变量不发射）、事务 transport 的 provenance 把关（MFD 限定 `include/linux/mfd/`，防止任意调用被误分类）。

### §5 受约束的 LLM 翻译与验证 — 后端与"不信任但可验收"

- **5.1 证据边界**：六个 JSON 节（driver/registers/modules/bind/constants/structs），FunctionSpec 角色物化为回调和状态绑定。
- **5.2 后端插件**：四后端（harness C / 裸机 C / Linux 模块 / Rust `no_std` + tock-registers）是自包含插件目录，新增目标无需改提取或验证——架构上兑现"多后端翻译框架"。
- **5.3 验证门**（论文的诚意所在）：编译 → **回执对账四性质**（存在性 / 恰好一次 / 种类匹配 / 摘要一致性）→ trace oracle（harness 全量比对；QEMU 后端子序列匹配 + 分支敏感变体）。图 2 用"界内四级检查 vs 界外灰色列出的**不确立性质**"显式划定声明范围。
- **5.4 有界修复**：结构化失败反馈（缺哪个 op_id、哪行编译错、哪个偏移不匹配）→ 重 prompt，预算 3 轮，耗尽记为就绪阻塞项。

### §6 评估 — 五个 RQ 支撑翻译主张，诚实报告边界

- **RQ1/RQ2 提取特征**（485 操作、77.7% 符号地址、73 RMW、123 条件、157 寄存器）+ 图 3 胶水占比——注意后者是**呼应 §2 动机**的量化，不是孤立的提取指标；并明确"这是内部特征化指标，不是相对人工真值的精确率/召回率"。
- **RQ3/RQ4 翻译与严格就绪**：编译（harness 19/19、裸机 19/19、Linux 18/19）与严格就绪（4/19、4/19、2/19）**刻意分离**（图 4）——"把未知变换、不安全动态地址当作阻塞项而非静默近似"，宁可少报成功也不把编译误当语义正确。
- **多源扩展**：3 个真实 USB 模块、19 TU、27,447 行，跨 TU 调用边 223/223 解析、68 个内部调用点如实报告未解析（93.0%）；dwc2 4,250 操作。
- **RQ5 端到端**：三个案例分工——edu（值级 oracle）、gpio-ftgpio010（逐回调 trace 序列 + 13/13 操作 + 8/8 寄存器）、**DesignWare APB SSI**（旗舰：IR 证据 + 功能状态 + 四后端 + 18 项机器可检清单，**未关闭项如实报告**：Linux 严格 Kbuild 失败、Rust 六项缓冲区数据流失败）。案例末尾回-design-rationale：早期迭代"寄存器顺序全对却传不出一个字节"直接催生了功能状态层——用失败故事论证设计必要性。
- 另附 zero-shot 留出集（12 驱动，树内 guard 强制未参与开发）：12/12 编译、7/12 严格就绪，作为泛化数据点。

### §7–8 讨论与结论 — "验证门确立了什么"

- §7.2 专节声明验证门**不**确立什么（守卫等价、任意额外访问、DMA/IRQ 竞争、生命周期），列明效度威胁与 `EXPERIMENT_DEBT.md`。
- 结论一句定调："结果支持的是一个**证据边界原型**，而非整个驱动的等价性"——把主张收在证据范围内。

## 三、与旧稿行文的关键差异（为什么旧逻辑有问题）

| 维度 | 旧稿（driver-harness/paper_draft.md）与 v1 | v2（正确） |
|------|--------------------------------------------|-----------|
| **定位** | "提取与规约提取"（v1 标题就叫 Extraction of ... Specifications） | **驱动翻译框架**（Reconstruction ... to Multi-Backend Targets） |
| **核心问题** | "精度 vs 重量级"的提取矛盾 | **"非确定性允许出现在哪里"** 的翻译边界问题 |
| **对比对象** | 自己的正则原型（自我升级报告） | **两个领域极端**：C2Rust 式规则翻译 vs 直接 LLM 翻译 |
| **组织骨架** | 四硬伤 P1–P4（原型的缺陷清单） | **证据契约**贯穿全文；四硬伤降级为 §4 内的技术要点 |
| **章节顺序** | 提取（§3）→ 规约（§4）→ 生成（§5）：提取优先 | **契约（§3）→ 提取（§4）→ 翻译验证（§5）**：先立翻译目标 |
| **LLM 角色** | 确定性生成为主，LLM 是修复引擎 | **LLM 是翻译器本体**，但被夹在两个确定性阶段之间 |
| **运行示例** | gpio-ftgpio010（简单 GPIO） | **DesignWare APB SSI**（多源 + IR 证据 + 功能状态 + 四后端）；ftgpio010/edu 降为确定性验证案例 |
| **评估主轴** | 提取指标（461 ops / 77 RMW…） | **翻译结果**：编译 vs 严格就绪、端到端 oracle、四后端案例；提取指标退为 RQ1/2 辅助 |
| **诚实策略** | "100% 覆盖"式强主张 | **编译≠就绪≠等价**三级分离；清单失败、未解析调用、效度威胁如实报告 |

旧逻辑的根本毛病：把"自己上一版原型做不好什么"当成了领域问题，导致论文变成 prototype 2.0 升级报告；正确的行文是把领域内两个极端的失败当作靶子，让自己的贡献（证据契约 + 受约束 LLM + 验证门）成为对领域问题的回答。

## 四、v2 的行文特点与修辞资产

1. **"重新表达而非重新解释"**（re-express, not re-interpret）——证据契约的定义句，全文反复回收。
2. **"有界"修辞体系**：有界证据、有界验收、有界修复、证据边界原型——所有主张都显式带边界，与 §7 的"不确立清单"首尾呼应。
3. **失败故事驱动设计论证**：edu DMA 事故论证直接 LLM 不可信；DW 早期迭代"顺序对却传不出字节"论证功能状态层必要性——每个核心设计都有对应的失败案例作动机。
4. **数字诚实**：编译/严格就绪差距（19/19 vs 2–4/19）不但不藏，反而画图（图 4）强调"是有意的"；DW 清单失败逐项报告。
5. **量化动机**：9.5% 设备核心 vs 90.5% 胶水的行级分类（图 3）把 §2 的定性论述变成可测量主张。
6. **编号结构体作为记忆点**：三层操作、三地址类、四性质回执、四后端、五 RQ、18 项清单。
