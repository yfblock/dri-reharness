# 问题分析与修复追踪（Issue Fix Tracker）

## 何时使用

用户要求分析问题、排查错误、修复 bug、调查异常行为或测试失败时，必须使用本 skill。

## 工作流程

### 1. 开始分析时：创建追踪文档

1. 若 `records/` 目录不存在，先创建它。
2. 检查 `records/` 下是否已有针对**同一问题**的追踪文档：
   - 有 → 继续在该文档上追加更新，不要新建。
   - 无 → 新建文档，文件名格式：`records/YYYY-MM-DD-<issue-slug>.md`
     - 日期为当天；`issue-slug` 为简短英文 kebab-case 标识，如 `records/2025-08-29-train-loss-nan.md`。
3. 初始内容使用下方【文档模板】，先填写已知的问题描述与环境信息，状态设为 `🔍 分析中`。

### 2. 分析过程中：随进展更新

每当有实质性进展时更新文档（不要只在最后一次性补写）：

- 提出并验证了一个假设 → 在「分析过程」记录验证方法与结论
- 定位到根因 → 填写「根因」，状态改为 `🛠 修复中`
- 修改了代码 → 在「修复记录」表格追加一行（时间、改动文件与内容、结果）
- 完成验证 → 勾选「验证」清单，状态改为 `✅ 已修复`
- 无法解决或需要用户决策 → 状态改为 `❌ 未解决` 或 `⏸ 暂停`，并在「后续事项」写明原因

每次更新同时刷新文档头部的「最后更新」时间。

### 3. 完成后：收尾

- 确认状态、根因、修复方案、验证结果均已填写完整。
- 在回复中告知用户追踪文档的路径。

## 文档模板

```markdown
# <问题标题>

- **状态**: 🔍 分析中
- **创建时间**: YYYY-MM-DD HH:MM
- **最后更新**: YYYY-MM-DD HH:MM

## 问题描述

<现象 / 报错信息 / 期望行为 vs 实际行为>

## 环境信息

<相关配置、版本、数据、复现命令等（如适用）>

## 分析过程

### 假设 1: <描述>
- 验证方法: <如何验证（命令、日志、断点等）>
- 结论: <成立 / 不成立，及证据>

## 根因

<定位到的根本原因；未定位则写"尚未定位"及当前进展>

## 修复方案

<方案描述及涉及的文件>

## 修复记录

| 时间 | 操作 | 结果 |
|------|------|------|
|      |      |      |

## 验证

- [ ] <验证方式 1，如：复现命令通过>
- [ ] <验证方式 2，如：相关测试通过，无回归>

## 后续事项

<遗留问题、风险、注意事项；无则写"无">
```

## 状态标志

| 标志 | 含义 |
|------|------|
| 🔍 分析中 | 正在排查根因 |
| 🛠 修复中 | 根因已定位，正在修改 |
| ✅ 已修复 | 修复完成且已验证 |
| ❌ 未解决 | 尝试失败或超出能力范围 |
| ⏸ 暂停 | 等待用户决策或外部条件 |

## 注意事项

- 一个问题一个文档；多个独立问题分别建文档。
- 记录要具体：给出实际的命令、文件路径、报错原文，而不是泛泛描述。
- 分析过程的失败假设同样有价值，保留不要删除。
