# 故障排查

基本原则：先确认失败发生在哪一层，再修复根因。完整系统至少包含输入解析、
extractor、profile/manifest、Kbuild、QEMU、guest module、subsystem test 和 unload
多个边界；不要只看最终 exit code。

## 1. 先收集状态

```bash
git status --short
git branch --show-current
./run.sh help
```

对 profile/QEMU 失败，先找报告和日志：

```bash
find artifacts -path '*matrix.json' -o -name 'qemu.log' | sort
python3 -m json.tool artifacts/profile-matrix/matrix.json
rg -n "insmod|rmmod|PROBE|BOUND|SUBSYSTEM_TEST|QEMU_RUN_DONE|Oops|BUG|WARNING" \
  artifacts/profile-matrix*/**/qemu.log
```

如果 shell glob 不被当前 shell 展开，改用具体目录或 `find ... -exec rg ...`。

## 2. `ModuleNotFoundError`

### 症状

```text
ModuleNotFoundError: No module named 'langgraph_workflow'
ModuleNotFoundError: No module named 'subsystem_test_reporting'
```

### 原因

直接从仓库根目录运行 Python 时，`src`、`qa` 和 `qa/verification` 可能没有进入
`sys.path`。

### 处理

优先使用：

```bash
./run.sh langgraph <source> --mode analysis
```

或显式设置：

```bash
PYTHONPATH=src:qa:qa/verification python3 -m pytest -q <tests>
```

如果仍缺 LangGraph：

```bash
python3 -m pip install -r requirements-langgraph.txt
```

## 3. libclang 错误

### 检查

```bash
python3 -c 'import clang.cindex; print(clang.cindex.Config.loaded)'
rg -n "LIBCLANG|clang" src qa README.md REPRO.md | head -100
```

### 判断

- `clang.cindex` 导入失败：宿主 Python package 缺失。
- 能导入但 AST 报错：检查 libclang 版本和 compile context。
- 目标使用架构专用 flags：需要对应的 Kbuild `.cmd` 或 compile database，不能手工
  删除 flags 让分析“先过”。

## 4. kernel prepare/build 失败

### 标准命令

```bash
./tools/build/prepare_kernel.sh build
```

### 检查

```bash
test -f vendor/linux/Makefile
test -f platform/kernel/build/arch/x86/boot/bzImage
grep -E 'CONFIG_COMPILE_TEST|CONFIG_ARM_AMBA|CONFIG_COMMON_CLK' \
  platform/kernel/build/.config
git -C vendor/linux status --short
```

AMBA 需要 `CONFIG_COMPILE_TEST=y`、`CONFIG_ARM_AMBA=y` 和
`platform/kernel/amba-compile-test.patch`。如果 patch 已应用，脚本应跳过重复应用；
不要手工改 vendor 文件后忘记记录 source/config 状态。

## 5. Kbuild/modpost 失败

先区分阶段：

- compiler error：通常是 generated source、include 或 kernel API 不匹配；
- modpost error：通常是 symbol、module name、`EXPORT_SYMBOL` 或 config 缺失；
- QEMU `insmod` error：Kbuild 已经通过，问题在 guest runtime 或 module dependency。

建议命令：

```bash
make -C platform/kernel/build \
  M="$PWD/<staged-module-dir>" modules
```

读取完整 stderr 和对应 `.cmd`，不要只看最后一行 `make: Error`。

## 6. QEMU 没启动或超时

### 检查

```bash
command -v qemu-system-x86_64
test -f platform/kernel/build/arch/x86/boot/bzImage
rg -n "timeout|QEMU 退出码|QEMU_RUN_DONE|panic|Oops|BUG" \
  artifacts/<matrix-dir>/<profile>/qemu.log
```

常见原因：kernel bzImage 不存在、QEMU/initramfs 工具缺失、guest init 没有执行到
`QEMU_RUN_DONE`、module init 卡住、test 超时或 guest panic/Oops。

## 7. `amba_device_add()` 返回 `-EBUSY`

### 证据

```text
REHARNESS_AMBA_DEVICE_ADD_FAILED ret=-16 ...
```

### 排查

```bash
rg -n "BIOS-e820|root bus resource|REHARNESS_AMBA_DEVICE_ADD_FAILED" \
  artifacts/<matrix-dir>/amba-generic/qemu.log
```

`-16` 表示 resource tree 冲突。AMBA fixture 通过
`request_resource(&iomem_resource)` 注册资源，不能随意选一个看似在 RAM 外的地址；
它还必须避开 PCI MMIO window 和其他 root resource。当前 QEMU 256M 配置使用
`0x180000000`，不要回退到 `0x10000000` 或只凭“RAM 范围”猜地址。

## 8. AMBA probe 返回 `-ENOENT`

### 证据

```text
probe with driver reharness_amba_sensor failed with error -2
```

同时 candidate 的 `REHARNESS_AMBA_DRIVER_PROBE` 不出现，说明 candidate callback
还没有执行。

### 根因

AMBA core 的 `amba_probe()` 会先执行：

```c
clk_get(&pcdev->dev, "apb_pclk");
```

没有 DT/firmware 的 synthetic device 找不到 clock 时返回 `-ENOENT`。

### 检查

```bash
rg -n "amba_get_enable_pclk|clk_get|apb_pclk|REHARNESS_AMBA_DRIVER_PROBE" \
  vendor/linux/drivers/amba/bus.c \
  qa/verification/device-registrar/amba-registrar.c \
  artifacts/<matrix-dir>/amba-generic/qemu.log
```

registrar 必须建立 fixed clock 和 `clkdev_create(..., "apb_pclk", "reharness-amba")`
映射，并在 unload 时按 device、lookup、clock 顺序清理。

## 9. Candidate module 加载成功但没有 bound

### 检查

```bash
rg -n "DRIVER_INSMOD|DRIVER_PROBE_BOUND|probe with driver|PROBE" \
  artifacts/<matrix-dir>/<profile>/qemu.log
```

按顺序检查：

1. registrar/fixture 是否 `insmod` 成功；
2. sysfs 中是否有 manifest 期待的 device；
3. module name 是否和 `runtime.qemu.module` 一致；
4. bus binding 的 `bus` 和 `device_glob` 是否匹配；
5. identity、device-id table、modalias 是否和 candidate registration contract 一致；
6. candidate probe 是否在 core 前置步骤中被 defer 或返回错误。

`DRIVER_INSMOD_RC=0` 只表示 module 注册调用返回成功，不表示 probe bound；必须
检查 `DRIVER_PROBE_BOUND=1`。

## 10. subsystem test 缺失或失败

### 检查

```bash
rg -n "REHARNESS_SUBSYSTEM_TEST|SUCCESS|missing|unexpected|metadata" \
  artifacts/<matrix-dir>/<profile>/qemu.log \
  artifacts/<matrix-dir>/matrix.json
```

检查 manifest 的 `test.subsystem.tests[]` 与 guest marker 是否一致：name、kind、
provider、required、return code、status/success marker。

provider catalog 只能提供受信任来源和 prerequisites，不能代替 test execution。
required test 缺失或失败会阻止 acceptance；optional test 失败不能被写成 required
capability 通过。

## 11. unload 失败

### 检查

```bash
rg -n "RMMOD|QEMU_RUN_DONE|busy|refcount|use" \
  artifacts/<matrix-dir>/<profile>/qemu.log
```

常见原因：candidate 还持有 device、workqueue、IRQ 或 subsystem reference；fixture
registrar 比 candidate 更早卸载；fixed clock/clkdev mapping 在 device unregister
前被删除；test 留下 fd、open device 或异步 work。

通用顺序应是：停止使用者和 candidate，卸载 candidate，再按 manifest fixture 的
声明顺序卸载 registrar/provider，最后输出 `QEMU_RUN_DONE`。

## 12. profile 是 `inconclusive`

`inconclusive` 不是通过，也不是一定有代码 bug。它表示当前证据不足以证明完整
runtime contract，例如 profile 可识别但没有 trusted fixture、manifest 缺少 required
identity、provider 不可用、trace/compile evidence 缺失，或 source digest 不能安全对齐。

查看：

```bash
python3 -m json.tool artifacts/<matrix-dir>/matrix.json
rg -n "inconclusive|reason|missing|failure" artifacts/<matrix-dir>/matrix.json
```

不要为了让 matrix 变绿而把 `matrix_required` 改成 false；只有在确实不属于默认
acceptance scope 时才这样声明，并在开发记录中说明理由。

## 13. pytest 直接收集失败

如果看到 vendored Linux selftest 顶层 argparse 拒绝 pytest 的 `-q`，说明 pytest
收集范围包含了 `vendor/linux/tools/testing/selftests`。使用仓库指定测试入口，或
显式选择 `qa/tests`：

```bash
PYTHONPATH=src:qa:qa/verification \
pytest -q qa/tests/test_profile_runtime.py \
  qa/tests/test_profile_matrix.py \
  qa/tests/test_driver_profiles.py
```

如果完整收集退出码为 137，先确认是系统资源终止还是某个测试实际失败；不要直接
把结果解释为功能回归。

## 14. LLM 调用失败

### 检查配置

```bash
env | rg '^REHARNESS_LLM_|^OPENAI_API_KEY' \
  | sed -E 's/(API_KEY=).*/\1<redacted>/'
```

确认模型、base URL、key、backend、`langchain-openai`、timeout 和 temperature 都
有效。不要在日志或最终报告输出实际 key。模型响应解析失败、源码 envelope 不合法、
contract 不匹配和 Kbuild 失败都应该保留为结构化 failure，不能手工替换成通过。
