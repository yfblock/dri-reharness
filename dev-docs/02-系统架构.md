# 系统架构

## 1. 总体数据流

```text
source C / multisource descriptor / schema-2 manifest
        |
        v
input normalization + driver profile registry
        |
        v
libclang AST + compile context + source accounting
        |
        +--> RIS (.ris)
        +--> DeviceSpec (.dspec / JSON)
        +--> Facts (.facts)
        +--> formal.json + generation-contract.json
        |
        v
LangGraph state graph
        |
        +--> analysis result
        +--> LangChain candidate generation / repair
        |
        v
backend lowering + candidate validators
        |
        v
Kbuild / registration AST / generation contract
        |
        v
ExperimentRunner + manifest-driven runtime adapter
        |
        v
QEMU guest + subsystem tests + unload + optional trace matching
        |
        v
structured accepted / failed / inconclusive report
```

每一层都保留自己的 evidence。下一层不能用“源码看起来像支持”替代上一层
缺失的结构化证据。

## 2. Extractor 和中间表示

### 2.1 libclang AST

`src/extractor/` 负责读取 C 源码和精确 compile context，分析 callback、registration
root、跨函数调用和有限深度 inline，以及 MMIO、regmap、I2C/SMBus、wrapper、宏、
地址算术、分支、循环和 RMW 数据流。

不能证明的语义必须保留为 `Top`、unsupported marker 或 blocked evidence，不能
静默删除，也不能为了让后端编译通过而伪造常量。

### 2.2 RIS

RIS 是 backend-independent 的正式交互表示，主要操作包括：

- `Read`、`Write`、`ReadModifyWrite`；
- `TransactionRead`、`TransactionWrite`、`TransactionUpdate`；
- `Cond`、`Loop`、`Delay`。

每个 leaf op 应带有稳定 `op_id`、source evidence、kind、width、address/value
precision、path 和 access domain。RIS 仍是 `.ris` 文本格式，JSON 主要用于附加
evidence、DeviceSpec、contract 和机器报告。

### 2.3 DeviceSpec、Facts 和 generation contract

- DeviceSpec 描述设备资源、状态、函数和后端需要的绑定。
- Facts 汇总源码结构、callback、resource、registration 和 subsystem 信息。
- generation contract 将允许生成的 operation 集合和 receipt 约束固定下来。
- 生成 C 中每个 Read/Write/RMW 必须对应 `op_id + canonical digest` receipt。

独立 oracle 会拒绝 missing、duplicate、unknown、rejected、kind mismatch 和
digest drift。候选可以编译，不代表它通过 contract。

## 3. Profile registry

`src/driver_profiles.py` 是总线/设备类型的声明式 registry。定义通常来自：

```text
benchmarks/driver-profile-definitions.json
        |
        v
profile id + bus + callback/resource tokens
        + identity patterns
        + registration contract
        + manifest template
        + required/optional capabilities
        |
        v
ProfilePlan
```

当前 runtime-ready profile：

| Profile | 代表性 fixture | 必需能力 |
| --- | --- | --- |
| `amba-generic` | synthetic AMBA device + fixed `apb_pclk` | registration, probe, subsystem, unload |
| `i2c-generic` | synthetic I2C adapter/client | registration, probe, transaction, unload |
| `mdio-generic` | synthetic `mii_bus` | registration, probe, unload |
| `network-generic` | generic `net_device` | registration, probe, subsystem, unload |
| `pci-generic` | QEMU EDU PCI device | registration, probe, unload |
| `platform-generic` | synthetic platform registrar | registration, probe, unload |
| `spi-generic` | synthetic SPI controller/device | registration, probe, transfer, unload |
| `usb-generic` | QEMU xHCI + USB serial/gadget | registration, probe, transfer, unload |
| `virtio-generic` | QEMU virtio block device | registration, probe, transfer, unload |

`serdev-generic` 已进入识别和静态流程，但没有 trusted runtime fixture，因此
`matrix_required=false`。这不是 runner 失败，而是明确的 runtime capability gap。

新增普通类型时，优先新增 catalog/profile/template/provider，不要在
`run_profile_matrix.py` 或 `scripts/qemu/qemu_run.sh` 添加按驱动名、源码名或总线名
硬编码的分支。

## 4. Manifest contract

schema-2 manifest 是一次实验的事实边界，声明 source path、语言、compile context、
backend、runtime adapter、profile、capabilities、fixture、registration contract、
QEMU policy、kernel modules、subsystem tests、trace fields 和 limits。

`src/experiment_manifest.py` 在构造 typed manifest 时做路径、字段、状态、模块参数
和安全性校验。未知字段或越界路径应在 manifest 阶段失败，而不是在 QEMU shell 中
被解释为任意命令。

## 5. LangGraph 和 LangChain

### 5.1 LangGraph

`src/langgraph_workflow/` 是编排层，不是新的语义分析器。graph 主要负责：

1. 规范化输入和 mode；
2. 调用 extractor 产生或复用 evidence；
3. 构造有限、带 provenance 的模型输入；
4. 在 generation/experiment 模式调用现有 pipeline；
5. 透传结构化 compile/runtime/trace 结果。

analysis 不调用模型。experiment 必须有 manifest。LangGraph checkpoint 只保存输入、
digest、artifact 路径、阶段事件和结构化状态，不应保存 secret。

### 5.2 LangChain bridge

`src/langchain_bridge.py` 对生成和 bounded repair 提供统一模型边界：

- 默认 backend：`langchain`；
- 当前模型：`gpt-5.6-luna`；
- 当前配置 endpoint：`https://ai.yfblock.cn/v1`；
- key：`REHARNESS_LLM_API_KEY` 或 `OPENAI_API_KEY`；
- implementation：`langchain-openai` 的 `ChatOpenAI`。

LLM 返回的源码必须先被解析、contract 校验、编译和 runtime gate 接受，不能因为
模型返回了看似完整的 C 文件就直接覆盖当前候选。

## 6. Backend 和 validation layers

### 6.1 确定性 backend

`src/generator/` 提供 harness、bare-metal、Linux 和 Rust bare-metal 生成路径。
确定性后端主要用于可复现 baseline、contract 验证和论文矩阵；它们不等同于任意
Linux 驱动都能自动翻译。

### 6.2 Linux registration AST

`qa/verification/linux_registration_ast_oracle.py` 和
`src/linux_registration_contracts.py` 检查 framework registration API、root table、
callback、identity field、typed object link、module init root，以及需要时的
device-id table、IRQ attach 和 direct IRQ contract。

“生成了一个 `struct ..._driver`”不是完整 registration 证明；实际注册调用和
callback link 必须闭合。

### 6.3 QEMU runtime

`scripts/qemu/qemu_run.sh` 只消费已经验证的 manifest-derived policy。它负责：

1. 准备 rootfs/initramfs；
2. 构建并加载 manifest 声明的 fixture modules；
3. 加载 candidate module；
4. 检查 binding/probe；
5. 编译或加载 manifest-owned subsystem tests；
6. 检查 test markers、Oops、warning、QEMU completion 和 unload。

runner 不应该知道 `amba`、`spi` 或某个具体驱动的私有规则。新类型应通过
profile plan、fixture、provider 和 manifest 表达。

### 6.4 Subsystem test report

`qa/verification/subsystem_test_reporting.py` 将 manifest 中声明的 test name 与
guest marker 按稳定 ID 对账，同时检查 kind、provider、required、return code 和
status。缺失、重复、未声明或 malformed marker 不会被当作通过。

`native`、`tool`、`kselftest` 和 `kunit` 是不同证据来源。某个 provider 被列入
catalog 只说明来源受信任，不说明测试已经运行成功。

## 7. AMBA synthetic fixture 的特殊依赖

AMBA core 在 `amba_probe()` 前会获取名为 `apb_pclk` 的 clock。x86 QEMU synthetic
device 没有真实 firmware/DT clock，因此 registrar 必须：

1. 使用不与 QEMU PCI resource tree 冲突的资源地址 `0x180000000`；
2. 注册 fixed clock；
3. 用 device name `reharness-amba` 和 connection id `apb_pclk` 建立 clkdev lookup；
4. 先 unregister AMBA device，再删除 lookup 和 fixed clock。

实现见 [amba-registrar.c](../qa/verification/device-registrar/amba-registrar.c)。
这套逻辑属于验证 fixture，不应被误解为对真实 AMBA 硬件设备树的通用替代。
