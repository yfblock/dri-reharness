本文件记录当前 `langgraph` 分支的重要开发决策、故障定位和验证证据。新记录应
使用日期、目标、证据、结论和后续动作，不要只写“已修复”。

## 2026-08-24：LangGraph/LangChain 编排层

### 目标

把原有 Pi Agent 功能迁移到 LangGraph + LangChain，同时保持 extractor、
ExperimentRunner、generation contract、Kbuild、QEMU 和 trace gate 的边界。

### 决策

- LangGraph 只负责 stateful orchestration，不重写 extractor 或 runtime adapter。
- analysis 模式不调用 LLM，便于无 key 环境验证静态 evidence。
- generation/experiment 模式通过 LangChain bridge 调用 OpenAI-compatible endpoint。
- LLM 候选不能绕过 contract、compile、runtime 和 trace acceptance。
- 旧 Pi path 仅在显式设置 `REHARNESS_LLM_BACKEND=pi` 时使用兼容路径。

## 2026-08-25：声明式 profile matrix

### 目标

让不同 Linux driver framework 通过统一 profile registry、manifest 和 QEMU runner
进入同一条验证路径，而不是继续添加按总线/驱动名分支。

### 已接入的 representative profiles

`platform`、`pci`、`i2c`、`spi`、`usb`、`virtio`、`mdio`、`network` 和 `amba`。

每类 profile 通过 catalog 声明 callback/resource evidence、identity、manifest
template、fixture、capabilities 和 subsystem test source。`serdev` 仍保留为
静态识别但 runtime-inconclusive。

## 2026-08-25：AMBA 接入和两阶段 QEMU 故障定位

### 阶段一：resource tree 冲突

初始 registrar 使用：

```text
start = 0x10000000
size  = 0x1000
```

QEMU guest 日志显示：

```text
pci root bus resource [mem 0x10000000-0xfebfffff window]
REHARNESS_AMBA_DEVICE_ADD_FAILED ret=-16 start=0x10000000 size=0x1000
```

`-16` 是 `-EBUSY`。根因是 AMBA resource 通过 `request_resource(&iomem_resource)`
进入 Linux resource tree，而初始范围位于已登记的 PCI MMIO window 内。

### 阶段一修复

根据同一次 guest e820/PCI 日志，选择 PCI 64-bit window 之后的：

```text
0x180000000-0x1800000fff
```

这是单变量修复：不改变 manifest、runner、AMBA ID 或 resource size。

### 阶段二：AMBA core clock 缺失

资源冲突消失后，registrar 可以加载，但 candidate probe 返回：

```text
probe with driver reharness_amba_sensor failed with error -2
```

而 candidate 自己的 `REHARNESS_AMBA_DRIVER_PROBE` 日志没有出现。阅读 pinned
kernel 的 `vendor/linux/drivers/amba/bus.c` 后确认，`amba_probe()` 在调用 candidate
`.probe` 之前调用 `amba_get_enable_pclk()`，该函数执行：

```c
clk_get(&pcdev->dev, "apb_pclk");
```

无 DT/firmware 的 synthetic device 找不到该 clock，返回 `-ENOENT`。

### 阶段二修复

registrar 增加 fixed clock、`clkdev_create(clock, "apb_pclk", "reharness-amba")`、
add failure cleanup 和 unload 顺序 cleanup。

最终 AMBA 日志包含：

```text
REHARNESS_AMBA_DEVICE_READY name=reharness-amba periphid=0x00100001
REHARNESS_AMBA_DRIVER_PROBE periphid=0x00100001 resource=0x1000
REHARNESS_DRIVER_PROBE_BOUND=1
REHARNESS_SUBSYSTEM_TEST_0_STATUS=pass
REHARNESS_DRIVER_RMMOD_RC=0
REHARNESS_RUNTIME_FIXTURE_MODULE_0_RMMOD_RC=0
=== QEMU_RUN_DONE ===
```

### 证据路径

- 初始失败：`artifacts/profile-matrix-amba-debug/amba-generic/qemu.log`
- resource 修复后的中间结果：`artifacts/profile-matrix-amba-fix/amba-generic/qemu.log`
- AMBA 最终通过：`artifacts/profile-matrix-amba-fix2/amba-generic/qemu.log`
- 完整矩阵：`artifacts/profile-matrix-final/matrix.json`

## 当前未闭合事项

- `serdev-generic` 没有可信 QEMU registrar/fixture，不能加入默认 runtime acceptance。
- 完整 `pytest -q qa/tests` 不是当前可直接声称通过的回归入口。此前观测到：
  vendored Linux selftest 被 pytest 收集时顶层 argparse 拒绝 `-q`，一次完整收集
  退出码为 137，另有冻结 extractor artifact 与工作树不一致、GPIO provider
  materialization 字段期望不一致等问题。
- 现有 profile 是代表性 framework contract，不覆盖整个 Linux 子系统的所有设备、
  IRQ、DMA、热插拔、错误注入、power management 和真实硬件路径。
- OpenAI-compatible endpoint 的 Chat Completions 兼容路径已经接入；Responses-only
  行为必须由当前 `langchain-openai`/服务端版本单独验证，不能从配置文件推断。
